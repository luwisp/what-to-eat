# 多人聚餐智能点菜 · 设计文档

- 日期：2026-10-16
- 状态：待评审

## 1. 概述

**产品**：一个解决"多人聚餐点什么菜"的 Web 应用，引入 agent 协助决策。店内扫码进局、全桌实时协同勾选忌口与偏好，agent 综合全桌约束给出推荐组合并支持对话调整。商家注册账号入驻、在专属界面录入菜品。

**定位**：创新比赛作品。

**架构语言**：后端采用华为自研仓颉（Cangjie）语言——团队明确决策，兼具"国产自研栈"叙事点；前端为静态 HTML/JS。

**成功标准**：

1. 核心闭环可用：建局 → 扫码进局 → 勾选偏好 → 实时聚合 → agent 推荐 → 对话调整
2. "忌口 0 违反"机制可演示：任何情况下硬约束不被突破
3. 降级兜底可演示：LLM 不可用时规则引擎仍能出推荐
4. 商家端完整可用：注册、登录、录入与管理菜品；C 端无需登录

**团队与周期**：1~2 人；周期不设死线（原 4 周参考已放宽，里程碑仅作参考）。范围仍按小规模狠收。

## 2. 背景与问题

多人聚餐点菜的痛点：忌口冲突（有人不吃辣、有人不吃香菜）、口味分歧、没人拍板。现有点餐系统只解决"下单"，不解决"决策"。

**创新点**：把"全桌实时协同"与"agent 决策"结合——每个人扫码表达自己的约束，agent 在全体约束的交集上做推荐；规则引擎保证硬约束永不违反，LLM 负责推荐、搜索与对话。

## 3. 核心概念

| 概念 | 定义 | 谁负责 |
| --- | --- | --- |
| **硬约束（忌口）** | 过敏、明确不吃：辣、香菜、葱、蒜、花生/坚果、海鲜、羊肉、内脏、素食等（可扩展标签集） | 规则引擎，100% 保证 |
| **软偏好** | 口味倾向（清淡/重口/麻辣…）、想吃/不想吃食材（非过敏级）、可选人均预算 | LLM 权衡 |
| **安全候选集** | 满足全桌所有硬约束的菜品子集 | 规则引擎产出，是 LLM 唯一可见的推荐空间 |

## 4. 系统架构

**技术栈**：仓颉（Cangjie）后端 + 静态前端。

- 后端语言：华为自研仓颉（SDK 默认 LTS 1.0.5），官方 `net.http` 标准库（HTTP/1.1 / HTTP/2 / WebSocket 服务器），社区备选 [tycj-net](https://gitcode.com/tybb2026/tycj-net/tree/)、[tycj-web](https://gitcode.com/tybb2026/tycj-web/tree/)
- 存储：[sqlite4cj](https://gitcode.com/AlonNas/sqlite4cj/tree/main)（CFFI 封装原生 SQLite，MIT）——W1 须在开发环境验证；**兜底：JSON 文件持久化**（1~2 家店演示规模完全够用）
- LLM：DeepSeek（openai 兼容接口），仓颉 HTTP client + JSON 手写调用，`llm.cj` 适配层可替换
- 前端：Vue 3 + Vite 构建、导出静态产物（默认选型，原生 JS 亦可），由仓颉 server 托管；浏览器原生 WebSocket（不用 socket.io，断线重连由前端手写：指数退避 + 重连后拉全量快照）

```
web/             用户端静态前端（Vue 构建产物，由仓颉 server 托管）
web/admin/       商家端静态前端（注册/登录 + 菜品管理界面）
src/main/        入口：HTTP + WebSocket server（net.http）
src/auth/        商家账号与登录会话（注册/登录/密码哈希/会话校验）
src/agent/       agent 层（核心创新点）
  ├─ llm.cj        LLM 适配器（DeepSeek 默认，可替换为其他 openai 兼容服务）
  ├─ rules.cj      规则引擎：纯函数，硬约束过滤/冲突检测/确定性推荐
  ├─ tools.cj      工具定义（搜菜/查菜/调整推荐）→ function calling
  └─ prompt.cj     提示词
src/store/       SQLite 存储层（sqlite4cj；兜底 JSON 文件）
src/model/       数据模型
```

**关键边界**：

- `rules.cj` 不依赖 LLM，**必须能独立产出确定性推荐**（降级路径与双保险叙事的基础）
- `llm.cj` 不关心业务，只负责"问模型要结构化 JSON"
- 实时层只做房间状态广播，不掺业务逻辑
- 每层可独立理解、独立测试（仓颉内置测试框架）

**生态风险与兜底**（W1 验证项）：

- sqlite4cj 在开发环境不可用 → 换 JSON 文件持久化，接口不变
- `net.http` WebSocket 遇坑 → 换社区 tycj-net / tycj-web
- 存储与网络只是实现替换，不影响上层设计（分层边界的意义所在）

## 5. 数据模型

- **MerchantAccount**：id、用户名、密码哈希（加盐）、restaurantId、创建时间（一个账号绑定一家餐厅，MVP 简化）
- **Restaurant**：id、ownerId（所属商家账号）、名称、简介
- **Dish**：id、restaurantId、名称、价格、图片、分类（凉菜/热菜/汤/主食/饮品）、食材[]、辣度 0-3、素食标记、忌口标签[]（含花生/香菜/海鲜…）
- **Session（聚餐局）**：id、短码（4~6 位字母数字，如 `A3F9`）、restaurantId、发起人昵称、状态（open/recommended/closed）、可选人均预算、创建时间、过期时间（24h TTL 清理）
- **Participant**：id、sessionId、昵称、头像色、忌口[]（硬约束）、软偏好{口味倾向、想吃食材、不想吃食材}、加入时间（同局昵称允许重复，以颜色区分；无账号体系，昵称即身份）
- **Recommendation**：id、sessionId、菜品[]、总价、每条推荐理由、生成时间、是否采纳
- **ChatMessage**：id、sessionId、sender、role（user/agent）、内容、时间（对话式调整历史，轻量持久化）

## 6. 核心流程与实时协议

**用户视角主流程**：

1. 发起人建局 → 得到短码 + 二维码 + 进局链接（扫码、输码或点链接均可进局）
2. 同桌人扫码/输码进局，起昵称
3. 各自勾选忌口（硬约束）+ 软偏好
4. 大屏实时聚合："3 人忌辣 · 1 人素食 · 2 人想吃鱼"
5. 任一成员点"开始推荐" → agent 出组合 + 每条理由 + 总价
6. 对话调整："换个不辣的鱼""再加个汤" → agent 调整 → 规则复检 → 结果页「忌口 0 违反」标记点亮
7. 确认定格：结果可投屏、截图，作为整桌的"决策凭证"

**实时协议（WebSocket）**：

- 客户端 → 服务端：`join_room(code, nickname)`、`update_preferences(prefs)`、`request_recommendation()`、`chat_message(text)`、`restart()`
- 服务端 → 客户端：`room_state`（成员 + 聚合偏好）、`recommendation_result`、`recommendation_started`（大屏仪式感动画）、`chat_delta`（流式回复）、`error`

**设计原则**：

- **全量快照广播**：任何变化广播完整 room_state，不做增量 diff；断线重连拉一次快照即恢复。简单即正确，稳定优先。
- **推荐单飞**：同一局同时只允许一个推荐任务进行中，新的请求返回"推荐进行中"状态。

## 7. 用户故事

### 7.1 C 端：一桌人从进店到点完菜

人物：小王（发起人）和 5 位同事。场景：周五晚公司聚餐，走进"蜀香居"。

1. **发起**：桌上摆着进店码，小王打开应用，选择餐厅"蜀香居"，点"发起聚餐"→ 生成短码 `A3F9`、二维码和进局链接。
2. **进局**：小王把链接发到微信群，大家点开/扫码进局，各自起昵称（头像色自动区分）——全程无需注册登录。
3. **勾选偏好**：小王勾忌口"花生"（过敏，硬约束），软偏好"想吃鱼"；小李勾"香菜""海鲜"；小张勾"辣"、口味倾向清淡；小刘选素食。每勾一项，大屏实时刷新聚合："5 人已加入 · 2 人忌辣 · 1 人忌香菜 · 1 人忌花生 · 1 人素食 · 2 人想吃鱼"。
4. **推荐**：小王点"开始推荐"→ "AI 正在综合全桌偏好…" → agent 给出 7 道菜组合（6 人桌：荤素搭配、含 1 汤 1 主食），每道菜带事实理由（"清蒸鲈鱼 · 微辣 · 满足 2 位想吃鱼的偏好"），总价 486（人均 81，预算 80 可接受），结果页亮起「**忌口 0 违反**」。
5. **对话调整**：小张在对话框问"鱼有没有不辣的？"→ agent 换成"番茄鱼 · 不辣"并复检 → 结果实时更新，标记依然 0 违反。
6. **定格**：全桌确认，小王点"确认这桌菜"→ 结果定格，截图发群、照单给服务员。
7. **（可选）重开**：有人临时加入或离开 → 发起人点"再来一局"重新召集。

**异常分支**：全桌 2 人忌辣而店内仅 4 道不辣菜 → agent 提示"可满足度有限"，列出可放宽项由全桌决定；断网或 LLM 不可用 → 自动切本地规则推荐，流程不断。

### 7.2 B 端：商家从入驻到上线

人物：张姐，"蜀香居"老板。

1. **注册**：打开商家端，注册账号（用户名 + 密码）。
2. **建店**：登录后创建餐厅档案：店名"蜀香居"、简介、营业信息。
3. **录菜**：逐道录入 25 道菜——名称/价格/分类/辣度/食材/忌口标签/图片；录完用"预览"查看用户端呈现效果。录入越准确（辣度、食材、忌口标签），顾客得到的推荐越贴合。
4. **上线使用**：顾客在店内发起聚餐局、选择"蜀香居"，agent 基于张姐录入的数据做推荐。
5. **日常维护**：今日特价、沽清下架随时增改，用户端即时可见。
6. **（后续可选）多店**：一个账号开多家店。

**异常分支**：忘记密码 → MVP 暂不做找回流程，由管理员后台重置。

## 8. agent 设计（核心创新点）

混合式三层：

| 层 | 职责 | 确定性 |
| --- | --- | --- |
| ① 规则引擎 `rules.cj` | 输入全桌忌口 + 菜品库 → 输出**安全候选集**、冲突检测（"该店仅 4 道不辣菜，是否放宽？"）、**确定性推荐**（荤素比约 6:4 + N 人约 N+2 道 + 价格区间 + 招牌优先；无 LLM 也可用） | 100% |
| ② LLM 推荐 | 安全候选集 + 软偏好 + 人数 + 预算 → DeepSeek 返回结构化 JSON（菜品/理由/总价）。**模型只能在候选集内选菜**，工具 `search_dishes` 也只检索候选集——从机制上保证忌口永不破 | 增强层 |
| ③ 对话调整 | 追问 → 工具调用（search_dishes / get_dish / adjust_recommendation）→ 每次输出前规则引擎复检 | 增强层 |

**防翻车细节**：

- LLM 输出经 JSON 结构校验（字段级手写校验器），失败重试 1 次，再失败走规则推荐
- 推荐理由**由模板从 DB 字段生成事实**（"清蒸鲈鱼 · 微辣，满足 2 位想吃鱼的偏好"），LLM 只润色不编造，杜绝幻觉
- 30 秒超时自动切本地规则模式，UI 明示"已切换本地推荐模式"（对话禁用，推荐可用）

## 9. 商家端

- 独立界面（`web/admin/`）；**C 端无登录**（扫码/链接进局、昵称即身份），**商家端需注册登录**
- **简单账号系统**：注册（用户名+密码，加盐哈希存储、不存明文）→ 登录 → 会话 cookie（token 落库、过期清理）
- 一个商家账号绑定一家餐厅（MVP 简化，多店后续可扩展）；登录后管理自家餐厅与菜品（增删改查）
- 菜品表单：名称/价格/图/分类/食材/辣度/忌口标签
- 预录 2 家店数据（对应 2 个商家账号），主打一家川菜馆 25 道菜
- 菜品图：自拍或占位图（注意网络图片版权）
- 找回密码：MVP 暂不做（由管理员后台重置）

## 10. 错误处理与降级

| 场景 | 处理 |
| --- | --- |
| DeepSeek 超时/限流/Key 失效 | 30s 超时 → 重试 1 次 → 切规则推荐，UI 明示"本地模式"（对话禁用，推荐可用） |
| 推荐 JSON 不合法 | Schema 校验失败 → 重试 1 次 → 规则推荐 |
| 约束冲突无法满足 | 规则引擎给出"可满足度"警告 + 例外选项，由全桌人决定放宽哪条——这是产品亮点，不是错误 |
| WS 断线 | 前端指数退避重连（原生 WebSocket 手写）+ 重连后拉全量快照 |
| 无外网（LLM 不可用） | 规则模式完整可演示（双保险叙事的实证） |
| 服务崩溃 | 房间落 SQLite，重启后按短码恢复 |

## 11. 测试策略

- **规则引擎单测**（仓颉内置测试框架）：忌口排除、素食桌、冲突检测、凑单份量——纯函数全分支覆盖
- **agent 层单测**：mock LLM 适配器，测 prompt 组装、JSON Schema 校验、一次重试、降级切换
- **工具安全测**：固定菜品库下 `search_dishes` 只返回安全候选集
- **关键路径 e2e**（Playwright，驱动浏览器、与后端语言无耦合）：建局 → 3 人进局 → 勾选 → 推荐 → 对话调整，一条脚本全跑
- **商家端 e2e**：注册 → 登录 → 录菜 → 用户端可见新菜品
- **真实 API 冒烟**：预录数据下跑 10 次真实 DeepSeek 推荐确认稳定

日期：2026-10-20。融合 B1 提供的界面输入/饭量方案，以及用户确认的个人适配、主食、预算档位、合理加菜/加份/加汤等约束。

**归属与范围：B2 的独立设计建议。核心选择器已接入正式推荐流程，并保留无元数据菜单的旧规则回退。**

**实现状态：正式流程已接入。** `src/agent/meal.cj` / `buildMealRecommendation` 实现饭量、独立主食、动态愿望、90%预算档位及有限搜索；`recommendMeal` 在菜单缺少推荐元数据时回退到 `buildRuleRecommendation`。账号默认设置 API 尚未扩展；自由文本只支持需本人确认的有限主食解释，不是通用自然语言解析。此前人工参考菜单不作为算法输出证据，自动行为由单元与正式应用测试校验。

## 1. 合并后的输入与持久化边界

### 1.1 可存入用户默认配置的长期要求

| 界面字段 | 建议结构 | 语义 |
| --- | --- | --- |
| 辣度：不吃辣/微辣/中辣/重辣/都可以 | maxSpiceLevel = 0/1/2/3/null | 接受辣度上限；“重辣”不表示一定想点重辣菜 |
| 喜好：选项或文本 | tastePreferences[] | 清淡、酸甜、咸香等软偏好，不覆盖限制 |
| 忌口：选项或文本 | avoidFoods[] | 香菜、葱、内脏、猪肉等个人不吃项 |
| 过敏：选项或文本 | allergens[] | 大豆、花生、鸡蛋、牛奶、小麦等，触发整桌过敏过滤 |
| 饭量：小/正常/大/特别大 | appetite = small/normal/large/extraLarge | 热菜需求系数 0.5/1/1.5/2 |

饭量可进入长期默认设置，但现有 `UserDefaultSettings` 和 B2 PUT 白名单还没有此字段；须由模型负责人统一增加字段、默认值、存储迁移和 API 校验，旧账号缺失时按 normal 回填。此文不表示当前 API 已接受 appetite。

已登录用户进入每家店时可预填默认要求；进入新局时复制到本人草稿，仍需本人提交后参与适配。已有房间草稿不能被登录/默认配置刷新覆盖。本次临时修改不自动写回默认设置；用户明确保存才更新长期字段。商家账号和请求体中的 userId 不授权代写。

### 1.2 每家店/每局的动态愿望

| 界面字段 | 搜索输入 | 作用 |
| --- | --- | --- |
| 想吃的食材 | wantedIngredients[] | 从本店菜单事实派生，满足适合提出者的食材愿望 |
| 想吃的特定菜 | wantedDishIds[]，套餐沿用 wantedSetMealIds[] | 按 ID 绑定本店/版本，不能随文本编造菜 |
| 额外想吃：小吃、饮料 | wantedExtras[]（dishId + quantity） | 可同时选择多种并明确每种份数；明确数量按原数处理，有预算时也可自动补充适配项，不抵热菜/主食数量 |
| 其他要求（文本） | note + 经本人核对的 structuredOverrides | 例如不想吃米饭、主食换面条、明确不要主食 |

这些内容属于本局，不写入账号默认配置。动态菜品/食材选项随 restaurantId/menuVersion 重建，换店后不能把旧菜 ID 当作新店愿望。菜单更新后愿望重新校验，并说明下架、缺失或冲突。

“想吃重辣”是 softWishesByMember.wantedSpiceLevel=3，与“最多能吃重辣”独立。一人不吃辣、另一人想吃重辣可同时成立，只要各自有适合的热菜。

### 1.3 食材选项如何生成

1. 合并本店可售菜单的食材；套餐从菜品组分取材，不产生新配方。浏览层可另显示不可售项，愿望提交需校验。
2. 做空白、重复和有证据的同义名称归一；大列表分组、搜索、折叠展示，不在默认页面铺满全部选项。
3. 对**想吃食材的展示列表**隐藏水、常规基础调料、没有具体含义的“配料包”等低信息项；`unknown` 不作为可满足的食材愿望。
4. 展示黑名单不能删改原菜 ingredients。花生油、酱油、调料/汤底及 unknown 仍参与过敏、忌口和完整性校验；过敏/忌口输入也不能共用该展示过滤。
5. 保留被合并原词与原菜的关联，用户可展开核对。是否展示盐、油等由可维护的 UI 词表决定，不由 AI 改写原配方。
6. 正向食材愿望和保守的风险匹配应分开：想吃鸡肉不能被只有鸡精/鸡油的菜自动算作满足。优先依赖已知主料标记；没有主料信息时仅对明确匹配的食材解释，不能声称满足某种主菜。

## 2. 饭量如何变成热菜需求

采用整数“半道菜单位”避免浮点误差：

| 饭量 | 系数 | halfDishUnits |
| --- | ---: | ---: |
| 小 | 0.5 | 1 |
| 正常 | 1 | 2 |
| 大 | 1.5 | 3 |
| 特别大 | 2 | 4 |

```text
U = 已提交成员的 halfDishUnits 之和
    + 2 ×（声明人数 N − 已提交成员数）
H = (U + 1) // 2              // 热菜基础份数 = ceil(饭量总和)
```

未提交或尚未加入者暂按 normal 估算菜量，明确标记“饭量/饮食要求待补充”；他们的草稿过敏、忌口、饭量都不能提前作为有效提交。当前模型声明人数不得低于实际成员数；服务已有相应约束。成员稍后提交饭量或其他要求时，按版本机制使旧推荐失效。

例子：

- 5 人均正常：H=5，主食默认 5 单位。
- 5 人饭量为小、正常、大、特别大、正常：0.5+1+1.5+2+1=6，H=6。
- 5 人均小：总和 2.5，H=3，主食仍默认 5 单位。
- 4 人中 2 人已提交“小”，另 2 人未提交：0.5+0.5+1+1=3，H=3；不得宣称已适配那 2 位未提交者。

**本版以热菜份数 H 替代旧设计的固定 N 道不同主菜。** 同一道热菜 2 份可贡献 2 份热菜，但个人选择覆盖仍只有 1 种；多样性另作软目标，防止全桌都靠一种菜加份。小吃、凉菜、汤、主食、饮料均不抵 H。特殊餐型需要另设显式策略，不能在搜索时静默互换。

饭量系数是团队约定的点菜估算，不是热量、营养或实际克重。不同热菜的一份未必等重，结果不能称为保证吃饱。

## 3. 主食与文本覆盖

主食默认每人 1 个适配的单人份单位，与饭量系数独立。按成员分别处理：

```text
staplePreference.mode = default / none / noodles / specified
stapleUnitsNeeded = 1，明确选择 none 时为 0
```

- “不想吃米饭”不能直接解释成“不要任何主食”；可表示换面，也可能不想吃主食，须在界面让本人核对解释。
- “不想吃饭、吃面条”可提取为“本次米饭换面条”，仍需本人可见、可修改；不要影响其他人的米饭。
- 明确“不要主食”后，该成员主食需求为 0；不能为了凑预算偷偷补米饭。这里是显式需求覆盖，不是预算不足时擅自删饭。
- 面条/包子等须有可信的单人份换算与个人适配。不能默认一只包子等于一碗饭。小麦过敏者不能因想吃面就绕过过敏规则。
- 固定套餐里已包含的可分配主食先抵扣，避免重复配饭。
- AI/解析器只提议 structuredOverrides，显示解释和冲突；未经用户核对的含糊文本不静默成为硬约束。既有过敏、忌口及辣度限制不能被文本愿望清除。

## 4. 必需的数据事实与职责

推荐器消费不可变菜单/成员快照，不直接查询 SQLite 或导入溯源表。由 B1/目录适配层提供以 dishId 为键、与 menuVersion 绑定的 MealMetadata：

| 字段 | 作用与缺失行为 |
| --- | --- |
| role | hotMain / coldMain / side / staple / soup / drink / unknown；只有 hotMain 抵热菜数量 |
| vegetableRole | vegetable / other / unknown，表示搭配角色，不代表素食适配 |
| stapleUnits | 每份可信单人主食单位数；未知 null，不自动换算 |
| primaryIngredients[] | 已核对主料，用于正向食材愿望；未知不猜配方 |
| soupGroupId | 同款汤不同规格分组，避免重复选大/中/小份 |
| servesMin/servesMax | 只记录有来源的共享规格，未知 null，不由价格推断 |
| source | 原分类、人工核对或原文说明，可回溯 |

现有 Dish.category=hot 包含小吃/鸡蛋，不能直接当热菜正餐角色。老乡鸡原表“热菜”映射 hotMain，“凉菜”映射 coldMain，“小吃/辅食”映射 side。普通“米饭”可核对为 stapleUnits=1。蔬菜角色也须核对；含猪油的蔬菜角色菜不因此变为素食。

大份老母鸡汤原文适合 4–5 人，可核对后记录；不能把该说明推广到其他汤。

### 食材归一需要补的漏洞

现有字符串匹配中，“猪肉”不自然匹配“猪排骨、五花肉、熟猪油”。须在共享字典补明确的猪源关联及测试。肉源不明的“午餐肉”不能断言必含猪，也不能给不吃猪肉者直接判 fit：应返回个人 uncertain，不计覆盖。

个人的肉源不确定与全局 unknown 不同，不能为了处理一位成员而把整道菜改成 unknown，导致所有过敏者触发另一种整桌排除逻辑。大豆/酱油、鸡蛋/蛋清、牛奶/乳制品、小麦/面粉等也需有证据的关联，不能用显示选项的简化代替校验。

## 5. 过滤、需求分配与完整方案

### 5.1 不可放宽的过滤

- 同店、可售、金额/数量合法；固定套餐所有组分存在且可售。
- 任一已提交者过敏命中食材（含调料/汤底），整桌排除相关菜及包含它的固定套餐。
- 任一已提交者有过敏要求时，含 unknown 的菜及相关固定套餐整桌排除；AI 不能清除 unknown。
- 普通忌口、素食、辣度按个人计算 fit/conflict/uncertain，不扩大成整桌交集；已知冲突优先。
- 愿望不能覆盖限制。想吃重辣、鸡肉、某道菜、小吃或饮料都必须适合提出者才算满足。

### 5.2 完整方案需要满足什么

1. 所有条目通过硬过滤，总价 C 不超过总预算 B=N×人均预算（预算存在时）。
2. 展开后的 hotMain 总份数不少于 H，不能用 side/soup/staple/drink 替代；重复份数不增加不同菜品覆盖。
3. 每位已提交成员至少有一种适配热菜；选择丰富度目标为 min(2,H)，作为软目标，不要求“小饭量”者必须独占一道菜。
4. 热菜的共享估算需求可以分配给成员：每份 hotMain 视为 2 个半道菜估算单位，只向 fit 成员分配；已提交成员需求为其 halfDishUnits。未提交者只预留正常份量，不称为实际适配。
5. 每人的主食需求按已核对的 staplePreference 满足；套餐内已有主食抵扣，多种主食须按适配关系分配。
6. 数量/种类和汤数在 policy 边界内；缺少角色、主食单位等事实须报缺口。

热菜估算分配与主食分配可各做一个小型二分流/匹配校验，防止总数够却都只适合某一个人。共享估算单位不是实际克重，分配说明不能宣传为真实食物分装或营养保证。

若只有 1 份菜适合“特别大”饭量成员，只有“该成员至少有一种菜”不够；估算分配也会发现他需要 4 个半道菜单位而当前适配供给不足。

### 5.3 额外项与预算模式

用户已允许合理加菜、加份和加汤。小吃、饮料可选择多种且每种可明确多份；多人对同一项的份数相加，人工明确数量始终按原数处理。有预算时，完整正餐结构仍明显低于目标档位，可自动加入对至少一位成员适配的小吃或饮料，并在结果中明确标注。自动选择优先让同一道非主食少于人数，单人时优先最多1份；若不同适配菜各取一份仍无法进入目标档位，才分散增加必要份数，单项保留12份的搜索安全上限。没有预算时不自动添加。额外项均不抵 H 或主食。

预算 B 是不可超过的上限；在更高优先级的需求与愿望相同后，最小化 B-C，使总价尽量接近 B。L=ceil(0.9B)=B-floor(B/10) 仍作为“进入目标档位”的报告阈值，但进入 [L,B] 后仍继续比较距预算上限的差额。未达到 L 的合法完整方案仍可返回，明确本次未找到更接近档位的方案，不擅自越界或清除限制。

## 6. 搜索专用请求与输出

复用 RuleInput 的菜品/成员/人数/预算与版本事实；以下是下一版搜索层的建议类型，不另建一套数据库实体：

```text
MealSearchRequest {
  ruleInput
  submittedAppetiteByMember
  confirmedStapleOverridesByMember
  mealMetadataByDishId
  softWishesByMember {
    wantedIngredients[], wantedDishIds[], wantedSetMealIds[]
    wantedExtras[] { dishId, quantity }, wantedSpiceLevel?
  }
  policy {
    requiredHotPortions = H
    defaultStapleUnitsPerPerson = 1
    allowExtraHotDishes = true
    allowExtraPortions = true
    allowSoup = true
    extrasOnlyWhenRequested = false when budget exists
    maxAutoQuantityPerExtra = 12
    preferredQuantityPerDish = max(1, people-1) // 人工明确数量除外
    budgetMode = closestToCap
    targetBudgetRatio = 0.90 // 仅用于报告是否进入目标档位
    // 初始可配置搜索边界，须实测评审，不是份量事实：
    maxHotPortions = max(1, 2*H)
    maxQuantityPerHotDish = 2
    maxSoupSelections = 1
    targetVegetableDishes = 1
  }
  searchLimits { beamWidth, maxExpansions, deadline }
}
```

份数上限须考虑已授权的套餐组分；本来就超过上限的固定套餐不能被偷偷截断，返回策略不适用或作为显式政策调整后重搜。蔬菜数是建议的搭配软目标，不是已确认的营养标准。

```text
MealSearchReport {
  draft                         // 沿用 RecommendationDraft
  status                        // complete / partial / noCandidate
  targetBandReached
  estimatedHotNeed = H
  estimatedHotSupply
  perMemberCoverageAndAllocation
  perMemberStapleAllocation
  roleOrDemandDeficits[]
  unmetWishes[]
  objectiveBreakdown
  expansions, elapsedMillis
  stopReason                    // exhausted / expansionLimit / deadline
  proof                         // heuristic；只有严格证明才写 exact/provedBound
}
```

搜索完整性、预算档位和超时是不同维度。complete 不等于生产 canConfirm；生产仍检查填写齐、房间/菜单版本与权限。appetite、主食覆盖、文字解释的确认和愿望变化都应使旧推荐失效。

## 7. 评分：完成用餐需求，再满足偏好和预算档位

完整方案与部分方案分开存档，不能让便宜而缺饭/缺菜的方案胜过完整方案。硬规则先过滤，不把过敏或超支作为可抵消的惩罚分。

完整方案采用分级比较，前项相同才看后项：

1. 未满足明确愿望的**人数**，再比较未满足的不同愿望数；包含动态食材、特定菜、额外项与想吃重辣。愿望先归一去重，不能靠多填重复愿望提高权重。
2. 每位成员的选择丰富度缺口，只奖励到 min(2,H) 种适配热菜。
3. 已核对的蔬菜角色等搭配缺口。
4. 是否进入90%–100%预算档位；预算始终不得超过 B。
5. 同一道非主食超过人数偏好上限的最大份数、总份数，以及超过 H 的额外热菜份数等适度性指标；人工明确数量与按人主食不受该偏好覆盖。
6. 距预算上限的差额 B-C；在档位和适度性相同后继续接近预算上限。
7. 其余口味、做法/角色多样性，再比较总价，最后稳定 itemType/itemId/quantity。

¥203 与 ¥225 对五人、人均45都达到档位；同样覆盖、搭配和适度性下，¥225 距预算上限更近。预算100内的¥95也优于同样需求下的¥59。没有预算时不计算预算差额，以需求、偏好、搭配和适度份数为主。

愿望是软目标；若某位过敏者想喝成分 unknown 的饮料，应解释该愿望不可满足，不能绕过整桌规则。多个互相冲突的明确要求须显示冲突，不能靠评分让硬限制失效。

部分方案先比较零覆盖成员数、个人估算分配缺口、主食/热菜缺口，再比较上述软目标；不得标为“全员适配完成”。

## 8. 搜索流程：需求驱动的多样性束搜索＋有限替换

### 8.1 预处理

一次缓存逐人逐菜三态适配、整桌排除、角色、展开组分/份数、价格和愿望贡献。套餐按套餐价计一次，组分不能重复加价。愿望不预先把适配冲突候选放回。

候选不能只取最便宜前 K 道；保留稀缺成员、主食替代、明确愿望、角色补缺和不同价位的可行项。84 菜第一版可全量参与。

### 8.2 基础需求搜索

用多种种子（稀缺成员、明确愿望、搭配）启动；先计入/预留每人主食替代所需成本。增加适配热菜/份数/套餐，补足 H 和逐人估算分配缺口。无需强制 H 种不同菜，但同样适配时通过丰富度与重复度避免单菜堆份。

旧贪心只作为候选种子，须按新结构、饭量与主食需求修复；未修复时只能放 bestPartial，不能作为完整方案回退。

### 8.3 达到基础结构后的扩展

- 加不同热菜、加已有热菜份数，受 maxHotPortions 和单菜上限限制。
- 加合适的共享汤或替换汤规格；同组大/中/小份互斥，不能同时购买来凑价。
- 为明确请求添加适配小吃/饮料；有预算时也可在基础结构完成后自动补充适配项以接近档位。只计愿望和成本，不改变热菜/主食供给。
- 1 换 1、1 换 2、套餐与相应单点替换，或删除多余项/份数；都重新计算价格与需求分配。

基础需求完成不是整个搜索的停止条件；仍可改善愿望、搭配并继续接近预算上限，但不得超过预算。

### 8.4 保留多样性与剪枝

按基础完成度、个人覆盖/分配缺口、搭配和支出档位分桶保留 beam，避免所有槽位被同质低价方案占满。初始束宽可评测 16/32/64，扩展数可评测1000/3000/10000，实测后选参数，不预先承诺时延。

桶只用于配额保留，不能把相同价钱/覆盖的不同菜直接视为等价。去重键为稳定排序的条目数量向量，以及会影响后续可行性的分配/汤规格状态。

可以剪掉硬冲突、超预算、超数量上限，以及剩余候选无法补齐某人需求的分支。补齐费用下界必须考虑共享与套餐，不能把每个人最便宜菜价直接求和；第一版下界宁取0，避免误剪。

保留全局 bestComplete/bestPartial；固定扩展上限为正常路径控制，单调 Deadline 为兜底。所有阶段共用预算，超时返回已经验证的结果并标注 stopReason。启发式没找到不等于证明不存在。

## 9. 接近代码的伪代码

```text
recommendMeal(request):
    validateInputVersionsAndConfirmedOverrides(request)
    demand = deriveHalfDishDemandAndPerMemberStaples(request)
    B = checkedMultiply(N, budgetPerPersonFen) if budget exists
    L = B - B / 10 if budget exists
    facts = cacheFitRolesIngredientsAndComponents(request)
    archive = {bestComplete: none, bestPartial: none}
    beam = diverseSeedsWithStapleReservationsAndRepairedGreedy(facts, demand)

    while beam not empty and expansion/deadline budget remains:
        next = []
        for state in stableOrder(beam):
            archive.consider(state, checkDemandAndAllocation(state))
            operations = hasDemandDeficit(state)
                ? hotAndStapleRepairOperations(state)
                : authorizedExtraSoupWishSwapAndDeleteOperations(state)
            for operation in stableOrder(operations):
                child = applyIncrementally(state, operation, facts)
                if violatesHardRulesBudgetOrPolicy(child): continue
                if optimisticDemandCompletionImpossible(child): continue
                if seenExactState(child): continue
                next.add(child)
                archive.consider(child, checkDemandAndAllocation(child))
                stop if common limits reached
        beam = stableDiverseTopK(next)

    for candidate in archiveScoreOrder():
        draft = validateRecommendation(ruleInput, candidate.items)
        meal = validateDemandStaplesAndMetadata(request, draft)
        if both agree with cached facts:
            return explicitReport(draft, meal, stopReason)
    return explicitSafePartialOrNoCandidate()
```

需求分配、完整校验、种子修复和替换均须计入共用时间/扩展预算，不在 deadline 后启动无界清理。计算在 Repository 写锁外进行，提交/确认仍复检 roomVersion/menuVersion。AI 解释只能基于最终事实。

## 11. 本轮案例与必须补的测试

### 11.1 参考案例

五人均正常、每人主食一份：H=5、主食5单位；人均45，总预算225，目标202.50–225。用户允许加菜/加份/加汤，且有花生过敏、不吃辣、不吃猪肉、想吃重辣的成员。

人工参考：冒菜29＋排骨25＋牛肉22＋鱼头15＋山药9＋虾20＋南瓜5＋大份鸡汤68＋米饭10=**203元**，其中7份热菜满足H=5且在初始2H上限内。午餐肉来源未确认，冒菜不计为不吃猪肉者适配；重辣鱼头须适合提出者。此例仅证明在这些元数据与政策下存在达到档位的方案，不要求算法输出同一组菜，也不证明最优。

若五人都选“小”，H=3，默认 maxHotPortions=6；上述7份热菜参考不能不经检查直接复用，需要重新搜索。饭量改变必须真正影响数量边界。

固定“5道各1份、不加汤”的旧反例中，未过滤的最贵5道正餐菜＋饭仅141，可据乐观上界证明到不了202.50；该证明不适用于已允许扩展的当前政策。

### 11.2 验收清单

1. 饭量四档、半单位整数求和/向上取整，所有小饭量、混合饭量、未提交正常预留；N与实际成员下限校验。
2. 长期默认预填、旧账号normal迁移、草稿/提交隔离、临时要求不自动回写，饭量/主食变化使旧结果失效。
3. 食材聚合归一与折叠搜索；隐藏水/配料包不删原配方、不影响酱油/花生油过敏或unknown规则。鸡精不能自动满足想吃鸡肉。
4. 小吃、凉菜、汤不抵热菜H；加份不增加种类覆盖；每人估算需求和主食可分配，而不只检查整桌总数。
5. 个人不要主食、仅米饭换面、含糊文本待核对，套餐主食抵扣；小麦过敏与面条愿望冲突。
6. 明确选择的小吃/饮料数量不被自动改变；有预算时可另加适配额外项接近档位。成分 unknown 遇过敏仍排除，结果须标明自动加购。
7. 猪肉/猪油关联、肉源不明的个人uncertain，不吃辣与重辣愿望共存；愿望不能覆盖硬限制。
8. 预算0/极低/无预算/金额边界、主食成本预留；同样需求、愿望和适度性下95胜59，225胜203，且始终不得超预算。
9. 套餐价/角色/主食不重复计数，同款汤规格互斥；元数据缺失、套餐超过数量边界时明确处理，不截断套餐。
10. 小菜单8–12项、有限份数的穷举oracle，比较完整性与目标评分；超时、输入顺序置换、版本复检、无完整回退与最终校验失败。
11. 真实84菜、多种人数/饭量/饮食要求，记录预处理/分配/搜索/最终校验时间、扩展数、预算达标率和机器信息，先实测再承诺性能。
